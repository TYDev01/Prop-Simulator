# PropFirm Synthetic Research Lab — Build Specification

> Master spec. Anything built in this repo must conform to this document, or this
> document must be amended first (with rationale) in the same change.

---

## 1. Mission

Build a tick-accurate simulator of a **strict prop-firm challenge** on Deriv synthetic
indices, and an **automated research loop** in which Claude Opus 5 trades that account
and evolves the strategy from the evidence its own trading produces.

- Primary instrument: **Volatility 75 Index** (`R_75`).
- Later instruments: **Boom 1000**, **Crash 1000**.
- Python owns data, execution, risk enforcement, and validation.
- Opus owns judgement, hypothesis generation, and strategy evolution.
- The seed strategy is a reduced form of Rayner Teo's M.A.E. framework (see §7).

The deliverable is **not** a profitable bot. It is a measuring instrument honest enough
to prove or disprove an edge, plus an audit trail of how the strategy changed and why.

---

## 2. Non-negotiable truths

These are properties of the instrument, not opinions. Any result contradicting them is
a bug until proven otherwise.

**2.1 — Vol 75 is a driftless random walk at constant 75% annualised volatility.**
No participants, no order flow, no sessions, no news. Generated by an audited RNG.

**2.2 — Every reward-to-risk ratio has exactly zero expectancy.**
For a driftless walk with stop at distance `a` and target at distance `b`:

    P(target first) = a / (a + b)

At 1:2 RR, win rate is exactly 1/3 and expectancy is `(1/3)(2R) - (2/3)(1R) = 0`.
At 1:3 it is exactly 1/4. At 3:1 it is exactly 3/4. All zero. The win rate always
self-adjusts to cancel the payoff. **You cannot escape via RR selection, exit rules,
or position sizing.** Add spread and every configuration is strictly negative.

**2.3 — Therefore, on Vol 75, the only real degrees of freedom are:**
risk per trade, trade frequency, and their interaction with the drawdown limits.
Entry logic can only reduce cost by reducing trade count.

**2.4 — Structural mechanisms cited by discretionary price-action methods do not exist here.**
Support/resistance is justified by trapped traders exiting at breakeven. There are no
trapped traders. Accumulation/distribution describe institutions. There are no
institutions. These components are dropped, not ported (see §7).

**2.5 — Boom/Crash are different physics.** Asymmetric jump processes with genuine
structure. Treat as a separate research programme; do not reuse Vol 75 conclusions.

## 3. Architecture

Three layers. The boundary between them is load-bearing.

### Layer 1 — Python: Sensor & Execution (deterministic, fast)
Fetches ticks, builds bars, computes features, detects candidate setups, executes
orders, and **enforces every hard risk limit**.

> Hard limits are `if` statements, never a judgement call. The daily-loss kill switch
> must be unreachable by any model output.

### Layer 2 — Opus 5: Trader / Risk Arbiter (candidate-triggered only)
Never on the tick path. Python detects a candidate; only then is Opus called with a
compact state packet. Target ~10–20 calls/day.

**Input packet:** bars across the three timeframes, precomputed features, open position
state, and account state — equity, day P&L, distance to daily loss limit, distance to
trailing max DD, days elapsed, progress to target.

**Output:** strict JSON, schema-validated. Malformed ⇒ no trade, logged as a failure.

    {action, direction, entry, sl, tp, risk_pct, confidence, invalidation, reasoning}

### Layer 3 — Opus 5: Research Loop (offline, batched)
Reads the accumulated trade log, proposes rule changes, which are then validated
deterministically before adoption. See §8.

### Dual-mode requirement
Everything runs in two modes: **deterministic core only** and **core + Opus overlay**,
on identical data, so the two can be A/B compared. If the overlay does not beat the
core, that is a finding and it must be reportable.

## 4. Data layer

**Source:** Deriv WebSocket API v3, `ticks_history`. Market data needs only an `app_id`.

**Rules:**
- **Never hardcode symbol codes.** Enumerate `active_symbols` at runtime and pin what is
  found. Deriv has renamed volatility symbols before.
- Verify the granularity list against the live endpoint; do not trust documentation.
- 5000 bars/ticks per request ⇒ page backwards on `end` timestamps.
- **Store raw ticks immutably. Derive bars locally. Never re-fetch.**
- Contract spec (contract size, min/max lot, tick value, min stop distance, swap) must be
  ingested from the broker, never hardcoded from memory.

**Phase 0 gate — the spread measurement.**
Compute observed spread as a fraction of per-bar sigma at each candidate timeframe.
This ratio is the tax on every trade and **it decides the final timeframe by arithmetic,
not preference.** Reference sigma at 75% annualised: Daily ≈ 3.9%, H1 ≈ 0.8%,
M15 ≈ 0.4%, M5 ≈ 0.23%.

## 5. Simulator

**Tick-level and event-driven. Bar-level backtesting is forbidden.** On a 75%-vol
instrument, whether the stop or the target was hit first *inside* a bar is worth a large
fraction of the result. Bar-level fills silently manufacture profit.

Required components:

- **Fill engine** — observed spread, slippage model, min stop distance, gap-through-stop
  handling. On Boom/Crash, spikes gap through stops; modelling them as clean fills is
  fantasy and is the single largest source of fake backtest profit.
- **Account ledger** — balance, equity, floating P&L, used/free margin, stop-out level,
  swap accrual at rollover.
- **Order model** — market/limit/stop, SL/TP, trailing stop, break-even shift, partials.
- **Clock** — broker server time. The daily-loss reset boundary is strategically
  significant and must be exact.

**Leakage is the primary correctness risk.** The feed is a strict cursor: bar-close only,
the forming bar excluded or explicitly flagged, features computed only from the visible
window. **Ship a deliberate leakage test** that injects a known future value and asserts
it never reaches the decision layer.

## 6. Prop firm ruleset (strict; all values config)

| Rule | Value |
|---|---|
| Account size | $100,000 |
| Phase 1 target | +8% |
| Phase 2 target | +5% |
| Max daily loss | 5% of day-start equity |
| Max total loss | 10%, **trailing on equity high-water-mark** |
| Min trading days | 4 per phase |
| Max duration | 30 days (P1), 60 days (P2) |
| Consistency rule | No single day > 40% of total profit |
| Daily reset | 00:00 GMT+2 |
| Funded split | 80/20, 14-day payout cycle |
| Challenge fee | $500 |

Equity-trailing drawdown is the harshest common variant: floating losses count against
you, so "let it breathe" approaches die. The **min trading days and consistency cap are
load-bearing** — see §9.2.

**Payout ledger** simulates the whole career, not one challenge: fee → P1 → P2 → funded →
payout cycles → breach → new challenge. Report expected 12-month net **after fees**.

## 7. Seed strategy

Reduced M.A.E. Deliberately simple; the loop is meant to evolve it.

**Dropped** (mechanism absent on synthetics, per §2.4): the 4 market stages; horizontal
S/R as predictive; candlestick reversal triggers as predictive; trendlines; the
trending-vs-retracement body-size analysis; the "obvious levels" discretion.

**Kept, repurposed:**
- **Structural stop placement** — stop beyond a swing. Retained as a *risk* tool: it ties
  stop distance to realised volatility, which is well-behaved at constant vol.
- **Multi-filter selectivity** — retained as *cost control*. Fewer trades, less spread.
- **Declared invalidation before entry** — retained as discipline.

Timeframes: **M15 entry / H1 structure / H4 bias**, pending the §4 spread measurement.

## 8. Research loop

Four cadences. Discipline and strategy are separate concerns; mixing them corrupts both.

| Cadence | Action |
|---|---|
| Per trade | Log feature vector at entry, decision, reasoning, declared invalidation, outcome, MAE/MFE |
| Daily close | Opus audits **rule adherence only**. No strategy changes at this cadence. |
| Every ~50 trades | Research cycle: **at most 2–3 hypotheses**, each pre-registered with predicted effect size and an explicit falsification criterion, written down *before* testing |
| On adoption | Version the strategy as a commit carrying rationale, evidence, and test result |

**Champion/challenger.** Never mutate the live strategy. The champion trades; challengers
run in parallel on identical data; promotion requires beating the champion out-of-sample
by a stated margin.

**Parallel accounts.** Run 100–200 simulated challenges simultaneously. Report the
pass-rate *distribution*, never a single path. This inoculates against "I passed,
therefore the strategy works."

## 9. Guardrails

### 9.1 Overfitting defenses (non-negotiable)

A loop that keeps whatever "worked" on the trades it just saw is an overfitting machine,
and on a zero-drift instrument it will manufacture false discoveries quickly and
convincingly. Four hard defenses:

1. **Strict partitioning** — discovery / validation / holdout. The holdout is touched
   exactly once, at the end.
2. **Pre-registration** — predicted effect recorded before the test. This also yields a
   **calibration score for Opus-as-researcher**: how often do its predictions come true?
   Track from day one.
3. **Running multiple-testing ledger** — never resets. The best of 50 tested ideas needs a
   far higher bar than the best of 3.
4. **Continuous controls** — random-entry (identical risk management) and synthetic-GBM
   at matched vol, running in parallel *always*, not as a one-off. Every adopted change
   must beat them on the same data.

### 9.2 The degenerate solution

With zero edge, spread cost scales with trade count, so **fewer and larger trades strictly
dominate**. Risking 5% to make 8% in a single trade gives P ≈ 5/13 ≈ 38% while paying
spread once; 200 small trades bleed several percent before starting.

The loop **will** find this. It is mathematically correct and strategically degenerate —
a well-shaped coin flip, not a strategy. The min-trading-days and consistency rules in §6
exist to block it. Do not relax them for convenience.

## 10. Objective function

- **Primary:** P(pass P1 → pass P2 → first payout), across N parallel accounts
- **Secondary:** expected 12-month net **after** challenge fees
- **Tie-break:** lower variance

Explicitly **not** total profit, win rate, or Sharpe. Optimising those under challenge
rules produces a martingale that passes often and blows up catastrophically.

## 11. Build order & acceptance gates

| # | Phase | Gate |
|---|---|---|
| 0 | Data layer | Symbols verified live; history paged to Parquet; **spread-to-sigma measured and timeframe fixed by arithmetic** |
| 1 | Sim engine | Tick-level fills; MT5 CFD math; ledger correct; **leakage test passes** |
| 2 | Rule engine + payout ledger | Breach detection exact; career fee accounting correct |
| 3 | Seed strategy + controls | Random-entry and GBM controls running in parallel from the start |
| 4 | Research loop | Pre-registration, validation gate, champion/challenger, version history |
| 5 | Boom/Crash hazard study | Runs early in background — see §12 |

### Expected outcome, stated in advance
Most likely finding: entries indistinguishable from random, expectancy ≈
−(spread × trade count). That is not failure. It redirects the work to optimising
P(pass) over risk geometry — a small, clean, exhaustively searchable space — and the
payout ledger then answers whether that probability beats the $500 fee.

## 12. Boom/Crash — run early, in parallel

**The headline question is the shape of the hazard function:**

    P(spike on next tick | N ticks since last spike)

- Flat (Poisson/memoryless) ⇒ tick-counting is worthless and the question is closed.
- Non-flat (Weibull, gamma, bounded) ⇒ waiting N ticks has genuine, computable edge.

Empirically answerable from a few million ticks. **If the hazard is non-flat it reorders
the entire roadmap**, so run it early rather than at Phase 5.

**Known hazard — the M.A.E. inversion.** Crash 1000 drifts up and spikes down, so a
trend-following read classifies it as a permanent uptrend and says *buy only*. Boom 1000
is the mirror and reads as a permanent downtrend, saying *sell only*. Applied faithfully,
the method goes **long Crash and short Boom** — collecting small steady drift while
standing in front of the spike. High win rate, maximum negative skew, and a single spike
gaps through the stop. Against a hard daily-loss limit this is the exact failure mode that
ends accounts.

This is roughly the inverse of conventional practice (buy Boom only, sell Crash only).
Conventional practice is not thereby proven right — both may be zero-EV by design — but
the two have **opposite skew**, and under drawdown rules skew is not cosmetic. Test all
three: M.A.E.-as-written, the inversion, and random entry.

## 14. Conventions

- Config over constants. Broker spec and firm rules are data, not code.
- Every number that reaches a decision must be traceable to a logged input.
- Reproducibility: seed everything; the deterministic core must replay bit-identically.
- Log the full Opus prompt and response for every call. That log is the research dataset.
- Report failures plainly. A negative result stated clearly is the product.
